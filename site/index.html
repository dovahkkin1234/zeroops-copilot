How It Works

Three agents on one LangGraph, sharing state, a tool catalog, and SQLite memory. The evaluator's give_up path is a first-class outcome: honest uncertainty beats a confident wrong answer.

Flow: Error → Triage (memory search + LLM classify) → if similarity ≥ 0.85 and same error type, L0 fast-path to Reporter; otherwise Planner → Tool Executor → Evaluator (loop up to 8×: continue back to Planner, hypothesize forward, or give_up — a first-class outcome) → Hypothesizer → Verifier (repro script) → Problem Manager (scan codebase for same pattern) → Reporter (Postmortem + Markdown). Memory (SQLite + embeddings): written after resolution, read at Triage.

The evaluator loop

After every tool call the Evaluator decides one of three things: continue (need more evidence), hypothesize (evidence is sufficient), or give_up (contradictory evidence or budget exhausted). give_up is a first-class outcome, not an error state. A correct "I don't know, here is what I tried" is a better signal than a confident wrong answer. This bounded ReAct loop — capped at 8 iterations — is what distinguishes the system from a linear chain.

Memory retrieval — Stack Overflow duplicate pairs

The episodic memory system (cosine similarity over all-MiniLM-L6-v2 embeddings) was evaluated on an external ground truth: Stack Overflow's own duplicate-close mechanism. 124 Python duplicate pairs; 83 unique originals in index. R@3 = 0.911: the correct original question is retrieved in the top-3 for 91.1% of real duplicate pairs using only local 384-dim embeddings with no fine-tuning. Normalisation Δ ≈ 0 on human-written SO questions (which rarely contain raw file paths or line numbers); the normalisation is designed for raw stack traces from production logs.

Caveats: 124 of 298 fetched pairs were usable (174 originals deleted or inaccessible on the SO API). SO texts are human-paraphrased, not raw stack traces — the retrieval task differs from production incident replay. No fine-tuning applied.

Limitations

Stated plainly, so a reviewer knows exactly what this is and is not.

  • Memory is flat embedding retrieval, not a knowledge graph — no cross-incident relationship modeling, no entity resolution, no GraphRAG.
  • No personalization or user modeling — every query is treated identically.
  • Benchmark is small (n = 5 bugs with results, 7 fixtures total), synthetic, and authored by the same person who built the agent — confidence calibration is self-reported, not externally validated.
  • This page demonstrates memory retrieval and the save contract in-browser. It does not run the LLM agent loop — that requires a model backend not available in a static page.
  • Repro execution (REPRO_EXECUTION_ENABLED) is off by default; the Verifier node generates a script but does not run it in this version.
  • No streaming UI for the investigation trace in this version.
  • Scoped to Python single-service synchronous stack traces only — distributed traces, async bugs, and infrastructure failures are explicitly out of scope.

What's Next

The three-agent pattern generalizes to the broader ITIL taxonomy — service requests, change management, and event correlation. Directions being considered for a reworked successor: graph-structured memory linking incidents to affected files, root-cause patterns, and commits (the missing piece for GraphRAG-style retrieval); a personalization layer that adapts routing thresholds and investigation depth to individual on-call engineers over time; a streaming investigation UI for human-in-the-loop review; and running the benchmark on broader, externally-sourced incident corpora to move beyond the current self-authored fixture set. These are directions, not commitments — the first version is what it is.
